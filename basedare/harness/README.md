# BaseDare engineering and learning harness

Start with the existing [Product Constitution](../brain-vault/00-control/product-constitution.md), [architecture](../docs/architecture.md), [financial canon](../docs/FINANCIAL_CANON.md), [Brain memory rules](../docs/basedare-brain-memory-schema.md) and [sprint audit](../docs/design/irl-growth-harness-2026-11-08.md). ## Operate

1. `npm run graphify:rebuild` after source edits. `npm run harness:check` runs the deterministic harness evaluations and checks required sources, duplicate nodes and dangling edges in the actual Graphify code graph. Existing CI still owns build, safety, auth, discovery, participation, review, social, business and migration regressions. This does not replace their checks.
2. `npm run harness:evaluate -- --suite qr --out /tmp/basedare-qr-evaluation-UNIQUE.json` runs the actual disposable PostgreSQL/handler journey and existing privacy tests. Other allowlisted suites: discovery, social, business, safety, all. Commands come from `scenarios.json`, run without a shell, have a ten-minute ceiling per command, stop on failure and retain private temporary logs. Production/provider environment variables are not inherited. This is an allowlist, **not an OS security sandbox**: run untrusted contributions in existing CI, not against founder credentials.
3. In the existing creator-attribution admin screen, select a bounded window and **Export aggregate harness evidence**. It covers authored free-adventure QR cohorts only and contains only source/window/unit/completeness and six counts. Other destination types have N/A participation stages, not zero conversions. No identities, emails, raw events, exact coordinates or venue/creator roster. Source overflow exports unknown counts. The declared source is not a cryptographic attestation; the founder reviews provenance. Entries and stage events remain browser-journey/target observations, not unique people.
4. `npm run harness:evaluate -- --observation /path/to/approved-export.json --out /tmp/basedare-plan-UNIQUE.json` validates the aggregate input and generates deterministic hypotheses. Each proposal includes the observed problem, evidence, confidence/uncertainty, user impact, scope, engineering complexity, safety risks, success criteria, required tests and rollback. Without an export, product evidence is explicitly unavailable and the planner requests evidence; it does not diagnose a broken funnel. An incomplete real export is handled separately. The example fixture is labelled synthetic. Plans do not claim measured lift or start experiments.
5. Choose one proposal, inspect the code graph and real source, use a named branch, preserve invariants and run relevant registered evaluations. Open a **draft PR** with the hypothesis, exact revision, evidence provenance, before/after behavior, test receipts, remaining gates and rollback. The current QR sprint is the first example of this workflow; the harness does not invoke an autonomous Codex runtime.
6. A reviewer other than the implementing agent reviews the diff and receipts. CI is an independent mechanical gate, not a substitute for that reviewer. The founder approves merge/deploy. Only then compare matched windows/channels/device conditions and record the result in `learning/journal.md`, using the experiment template. Small samples, bots, consent, missing renders and frozen attribution prevent causal claims.

Reports must be new `.json` files outside the application source tree; existing files are never overwritten. Review and copy only sanitized observations/decisions into version control. No secrets or raw customer records belong in the harness.

## Current scope and controls

- Observe: existing tests, code graph and explicitly exported aggregate QR signals.
- Diagnose: bounded source/stage checks and reviewable proposals. P0 measurement uncertainty precedes P1 usability investigation and P2 invitation hypotheses. These priorities are triage rules, not a calculated expected-value score or evidence that one variant wins.
- Implement: a human/Codex collaborator uses existing tools on an isolated branch. No recursive self-modification or automatic commits, PR creation, merges, deploys, sending, contracts or money movement.
- Evaluate: meaningful existing suites plus harness negative controls; local canonical destination tests detect unavailable hosts, revoked/transferred identities and cancelled/expired sources. Tombstones are retained and never automatically repaired/deleted. No runtime graph database or automatic production DB access.
- Learn: version-controlled hypotheses and verified engineering findings; actual product outcomes stay NOT MEASURED until field evidence exists.

There is no scheduled autonomous worker, new telemetry collector, extra model service, production credential, payment authority or new login provider. Founder approval remains mandatory for production. Real-phone, provider, moderation, consent, withdrawal and financial gates remain intact.

Later autonomy requires trustworthy real telemetry, consented field use, a named independent reviewer and explicit founder controls. First prove one real QR → useful guest action → voluntary invitation → returning participant loop.

## Interpretation and experiment review

The approved observation schema is unchanged: `source`, `windowStart`, `windowEnd`, `complete`, `unit`, and exactly the six `counts` fields in `evaluate.mjs`. Do not append identities, device rows, query text, experiment assignments, WVRP or guardrail counts. A complete observed zero is distinct from incomplete/unavailable (`counts: null`); a zero denominator yields a null rate. Non-adventure participation is N/A, never a failed conversion. The six totals cannot establish distinct individuals, return participation, independent recipient starts, verified visits or business revenue.

The planner always reports cohort comparability as `not_assessed_from_aggregate` and guardrails as `not_measured`. A coherent or large aggregate never clears those review gates. Its only reported ratio is descriptive starts per landing; it does not compute lift, p-values or confidence probabilities. Sample thresholds are investigation heuristics. The report lists the provenance, unit, source/channel, inventory, device/network, consent, timezone/window and attribution checks a reviewer must assess separately. Use the same review requirements for the measurement-only proposals.

Before a field experiment, record a baseline revision, qualified denominator, outcome, comparable windows/cohorts and stopping rule. Set concrete acceptable limits for complaints, completion quality, moderation burden and reliability **before** observing results. Any privacy, consent, eligibility or payment-policy failure stops the experiment regardless of clicks. Guardrail evidence stays unknown unless actually observed; do not mark a report PASS by editing generated fields. Preserve negative and inconclusive outcomes in the journal. At small scale, use observed usability tasks instead of choosing an A/B winner.

[Experiments A–E](experiments/discovery-learning.md) are a proposed backlog, not activated assignments or authorized outreach. Use the [experiment record](experiments/template.md) for each reviewed attempt. The [research and measurement specification](../docs/design/discovery-research-2026-11-09.md) distinguishes verified source observations, hypotheses, current event coverage and proposed metrics. The Constitution's weekly known identities completing meaningful actions remains the product authority; WVRP is proposed, not an installed or current KPI.

## Change-aware quality gate — November14

Use `node harness/run.mjs --suite auto --base origin/main --plan-only true --out /absolute/new-quality-plan.json` to plan reviewed registered checks. Omit `--plan-only true` to execute the deduplicated commands. Unknown runtime paths fail the automatic plan and need an explicit reviewed suite mapping. `--suite buyer` exercises actual owner/privacy/parked-write DB cases and funding/payment presentation. CI saves the plan, buyer results and sanitized local-test logs as quality-evidence artifacts. No production credentials are inherited.

Reports state CODE_GRAPH_ONLY, PLAN_ONLY or REGISTERED_SCENARIOS. A graph-only run never claims user-journey tests, and releaseReady always remains false: browser/device/provider, review, exact CI and founder release decisions are outside this offline runner. Source content and revision are fingerprinted; code changing during a run invalidates the receipt. Failed commands stop execution and retain exit/signal/timeout information. Unknown product evidence stays unknown; no automatic code edit, outreach, PR submission, merge or deployment occurs.

The buyer visual fixture is optional: run `scripts/render-buyer-workspace-fixture.tsx` through the existing ts-node test runtime with JSX enabled after a build. It serves only synthetic SSR layout on127.0.0.1:3222. Its native disclosures can be checked at320/390px; it does not prove wallet connection, live customer data or payment. Actual API authority is checked independently by the disposable database suite.
